# Polyglot Repositories - Complete Architecture Guide

## Overview

Polyglot Logger is organized as a **modular monorepo** where the Go core and each language binding are independent, versioned Git repositories connected via Git submodules.

```
┌─────────────────────────────────────────────────────────────────────┐
│                     polyglot-go (Core)                              │
│        Single source of truth for ABI, codegen, logging logic       │
│                                                                     │
│  ├── api/abi.json ─────────────────┐                               │
│  ├── cmd/codegen ──────────────┐   │                               │
│  ├── internal/logger/          │   │                               │
│  └── native/                   │   │                               │
└───────────────────────────────┼───┼──────────────────────────────┘
                                │   │
                    ┌───────────┘   └──────────────┐
                    │                              │
        ┌──────────┴────────┐      ┌──────────────┴─────────┐
        │                   │      │                        │
        ▼                   ▼      ▼                        ▼
    polyglot-node      polyglot-py            polyglot-csharp
   (Git Submodule)   (Git Submodule)         (Git Submodule)
   npm @polyglot     pip polyglot-logger      NuGet Polyglot.Logger
   /logger           (bundled binaries)      (bundled binaries)
```

## Repository Details

### 1. Core: polyglot-go

**URL:** [https://github.com/kishankumarhs/Polyglot.git](https://github.com/kishankumarhs/Polyglot.git)

**Purpose:** Central repository containing:
- Go logger implementation (`internal/logger/`)
- CGO native exports (`native/`)
- C ABI contract (`api/abi.json`)
- Code generation tool (`cmd/codegen`)
- Submodule definitions (`.gitmodules`)

**Key Responsibilities:**
- Define the stable C ABI v1 contract
- Implement core logging, async queue, sinks
- Generate C header and FFI bindings for all languages
- Maintain build scripts for cross-platform native compilation

**Development Cycle:**
- Changes to `api/abi.json` → run `go run ./cmd/codegen` → updates all binding FFI files
- Changes to `internal/logger/` → no direct impact on bindings (ABI stable)
- New `//export` functions → update `api/abi.json` → codegen → test in bindings

**CI/CD:** GitHub Actions for:
- Go tests
- Native builds (Linux, macOS, Windows)
- Code generation verification
- Integration tests across bindings

### 2. Node.js Binding: polyglot-node

**URL:** [https://github.com/kishankumarhs/polyglot-node.git](https://github.com/kishankumarhs/polyglot-node.git)

**Type:** Git Submodule at `bindings/node/` in core

**Package:** `@polyglot/logger` on npm

**What It Includes:**
```
polyglot-node/
├── src/
│   ├── index.ts                    (Main entry point, auto-init)
│   ├── auto-init.ts                (Config discovery, library resolution)
│   └── ffi.generated.ts            (Generated FFI bindings - DO NOT EDIT)
├── test/
│   └── smoke.test.js               (Binding tests)
├── bin/                            (Pre-compiled native binaries)
│   ├── liblogger.so               (Linux x86_64)
│   ├── liblogger.dylib            (macOS x86_64 & arm64)
│   └── logger.dll                 (Windows x86_64)
├── dist/                           (Compiled JavaScript)
├── package.json                    (npm metadata)
└── README.md                       (Package documentation)
```

**Key Features:**
- ✅ Auto-discovers `polyglot.yaml` in project root
- ✅ Cross-platform binary resolution (Windows/macOS/Linux)
- ✅ Module-level initialization on import
- ✅ Bundled native binaries in npm package
- ✅ TypeScript definitions included

**Publishing:**
- Tag format: `v*.*.* ` (semantic versioning)
- GitHub Actions publishes to npm automatically
- Binaries sourced from core repository's cross-platform builds

**Development:**
- Located at `bindings/node/` in core
- Changes committed to polyglot-node repository
- FFI generated by core's codegen (read-only files)

## How They Work Together

### Code Generation Flow

```
1. Developer edits api/abi.json (core)
                    ↓
2. Run: go run ./cmd/codegen
                    ↓
3. Codegen verifies ABI consistency
                    ↓
4. Generates:
   - native/include/logger.h
   - bindings/node/src/ffi.generated.ts
   - bindings/python/polyglot_logger/_ffi_generated.py
   - bindings/dotnet/Polyglot.Logger/NativeMethods.Generated.cs
                    ↓
5. Submodule detects changes
                    ↓
6. Commit & push in each binding repo
                    ↓
7. Update submodule references in core
```

### Build & Release Flow

```
1. Developer tags core: git tag v0.3.0
                    ↓
2. GitHub Actions in polyglot-go:
   - Compiles natives for all platforms
   - Organizes binaries per binding
                    ↓
3. Each binding's GitHub Actions:
   - Pulls latest native binaries
   - Packages with generated FFI
   - Publishes to registry (npm/PyPI/NuGet)
                    ↓
4. Result: Three independent packages all at v0.3.0
   - npm: @polyglot/logger@0.3.0
   - PyPI: polyglot-logger==0.3.0
   - NuGet: Polyglot.Logger 0.3.0
```

### Configuration Discovery Flow

When a user installs any binding, it auto-discovers project configuration:

```
import { Logger } from "@polyglot/logger"
                    ↓
On module load: autoInitialize()
                    ↓
Search: /cwd/polyglot.yaml
        /cwd/../polyglot.yaml
        /cwd/../../polyglot.yaml
        ... (climb to root)
                    ↓
Found? → Pass path to native logger_create_from_config_file()
Not found? → Check POLYGLOT_CONFIG_PATH env var
            Check POLYGLOT_CONFIG_FILE env var
            Use safe defaults
                    ↓
Logger ready - no user config code needed!
```

## Development Workflows

### Scenario 1: Fix Bug in Python Binding

```bash
# Clone core with all submodules
git clone --recurse-submodules https://github.com/kishankumarhs/Polyglot.git
cd Polyglot

# Navigate to Python submodule
cd bindings/python

# Make changes
vim polyglot_logger/auto_init.py

# Test
pytest tests/

# Commit in the binding
git add polyglot_logger/auto_init.py
git commit -m "fix: path traversal in auto-init"
git push origin main

# Back to core, update reference
cd ../..
git add bindings/python
git commit -m "chore: bump python binding"
git push origin main
```

### Scenario 2: Add New ABI Function

```bash
# In core repository
cd Polyglot

# 1. Update ABI contract
vim api/abi.json

# 2. Implement in Go
vim internal/logger/logger.go

# 3. Add CGO export
vim native/export.go

# 4. Run codegen (updates all bindings)
go run ./cmd/codegen

# 5. Commit to core
git add api/abi.json internal/logger/logger.go native/export.go
git commit -m "feat: add new logging function"
git push origin main

# 6. Commit generated changes to bindings
git submodule foreach 'git add . && git commit -m "chore: regenerate FFI" && git push'
```

### Scenario 3: Release All Bindings Together

```bash
# In core, update version everywhere
vim api/abi.json  # Update abi_version
vim bindings/node/package.json  # Update version
vim bindings/python/pyproject.toml  # Update version
vim bindings/dotnet/Polyglot.Logger/Polyglot.Logger.csproj  # Update version

# Commit to core
git add .
git commit -m "chore: release v0.3.0 - all language bindings"

# Tag and push (triggers all GitHub Actions)
git tag v0.3.0
git push origin main v0.3.0

# Results:
# - npm publishes @polyglot/logger@0.3.0 automatically
# - PyPI publishes polyglot-logger==0.3.0 automatically
# - NuGet publishes Polyglot.Logger 0.3.0 automatically
```

### Scenario 4: Release Only One Binding

```bash
# Each binding has independent versioning!
cd Polyglot/bindings/node
npm version minor  # Updates package.json
git add package.json
git commit -m "chore: release v1.1.0"
git tag v1.1.0
git push origin main v1.1.0

# GitHub Actions in polyglot-node publishes to npm
# Other bindings unaffected
```

## File Ownership & Responsibilities

### Core Repository (polyglot-go)

**You write:**
- `api/abi.json` - C ABI contract (single source of truth)
- `internal/logger/` - Go implementation
- `native/export.go` - CGO exports
- `cmd/codegen/main.go` - Codegen logic
- `.github/workflows/build-binaries.yml` - Native compilation & distribution

**You regenerate (via codegen):**
- `native/include/logger.h` - C header
- All binding FFI files

**You do NOT write:**
- Binding-specific code (that's in submodule repos)
- Individual package.json, pyproject.toml, .csproj files (updated via codegen)

### Each Binding Repository

**You write:**
- Hand-written SDK classes & ergonomic APIs
- Binding-specific tests & examples
- Language-specific documentation
- README.md specific to that binding

**Codegen writes (read-only):**
- FFI bindings files (e.g., `ffi.generated.ts`)
- Type definitions

**You do NOT write:**
- ABI contracts (comes from core)
- Native library code (comes from core builds)

### Clone Everything

```bash
git clone --recurse-submodules https://github.com/kishankumarhs/Polyglot.git
```

## Version Management

Each binding maintains independent semantic versioning:

```
Core:    v0.3.0  (ABI version, affects all bindings)
Node:    v1.2.3  (Independent npm version)
Python:  v2.1.0  (Independent PyPI version)
.NET:    v3.0.1  (Independent NuGet version)
```

Typically all bindings release together on core updates, but they CAN release independently:

```
Scenario: Bug fix in Python only
- Python: v2.1.1 (new)
- Node:   v1.2.3 (unchanged)
- .NET:   v3.0.1 (unchanged)
```

## Troubleshooting

**Q: After cloning, `bindings/` folders are empty**
- A: Run `git submodule update --init --recursive`

**Q: Changes in one binding don't appear in core**
- A: Commit & push in the binding first, then update submodule reference in core

**Q: Codegen output is stale**
- A: Run `go run ./cmd/codegen` in core repository root

**Q: Package not installing from registry**
- A: Check binaries are bundled: `npm ls @polyglot/logger`, `pip show polyglot-logger`, etc.
